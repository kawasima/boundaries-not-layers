# 「なんとなくドメインモデル」から抜け出すための<br>本物のドメインモデリング入門

kawasima / 株式会社ウルフチーフ

<!-- _class: veil -->

## なんとなくドメインモデル

Value Object、Entity、Repository、Domain Service。ドメインモデリングとは、こういう部品を並べることだと読める情報は少なくない。

- 名前のついた型は増える
- パッケージも domain / usecase / infrastructure に分かれる
- レビューも通る
- それでも業務の決めごとがモデルのどこにも書かれていない、ということが起きる

---

<!-- _class: veil -->

## 業務の決めごとは、モデルの外へ出ていく

| 業務で決まっていること      | コードでの置き場      | 起きること                   |
| --------------- | ------------- | ----------------------- |
| どの値が有効か         | DTOのアノテーション   | ドメインの型は不正な値を作れる         |
| どの状態の組み合わせがありうるか | 区分フィールドと null | 型にない組み合わせが実行時に現れる       |
| どの操作が許されるか      | Service の if  | 呼出側は条件を知らないと使えない        |
| 業務上の却下がどう伝わるか   | 例外・boolean    | 扱いを書かなくてもコンパイルが通る       |
| いま何時か・DBに何があるか  | DIコンテナ        | 判断とI/Oが同じ関数に入る          |

個々のコードは妥当でも、業務規則はコードベース全体にまたがる暗黙の規約になる。

以降、この表の各行を `examples/` の実際のコードで見ていく。

## 有効な値は、境界のアノテーションに書かれる

```java
public record OrdererForm(
        @NotBlank @Pattern(regexp = "individual|corporation") String type,
        @NotBlank @Email String email,
        String name, String companyName, String corporateNumber) {

    @AssertTrue(message = "法人の場合は corporateNumber（13桁）が必須です")
    public boolean isCorporateNumberValidForCorporation() {
        return !"corporation".equals(type) || (corporateNumber != null && corporateNumber.matches("\\d{13}"));
    }
    // 「個人なら name 必須」「法人なら companyName 必須」も同じ形で足していく
}
```

<span class="src">[performance-purity/web/OrdererForm.java](https://github.com/kawasima/boundaries-not-layers/blob/main/examples/performance-purity/src/main/java/com/example/cart/web/OrdererForm.java#L16-L37)</span>

個人か法人かで必須項目が変わるという業務ルールは、フィールド単位の制約では書けない。だから `@AssertTrue` のクロスフィールド検証を人手で足す。項目が増えるほどこの手当ても増える。

そして、これは Web の型に付いた検査であって、ドメインの型は何も知らない。

## ドメインの型は、不正な組み合わせを作れる

```java
// domain 層。区分と、個人・法人 両方の項目をフラットに持つ
public record Orderer(OrdererType type, String email,
                      String name, String companyName, String corporateNumber) {}

// 法人なのに法人番号が無い注文者が、そのまま作れる
new Orderer(OrdererType.CORPORATION, "a@b.com", null, null, null);
```

<span class="src">[performance-purity/domain/Orderer.java](https://github.com/kawasima/boundaries-not-layers/blob/main/examples/performance-purity/src/main/java/com/example/cart/domain/Orderer.java#L12-L17)</span>

区分は本来、境界で個人か法人かを見分けるためのタグで、ドメインの状態ではない。型を分けないと、その区分をドメインまで持ち込むことになる。

## 純粋性をレイヤーの性質と見ると、三択になる

同じカート機能を、不変条件「合計数量が上限を超えない」の守り方だけ変えて3通り実装した。

| 実装                       | 諦めたもの | どこに出るか                    |
| ------------------------ | ----- | ------------------------- |
| performance-completeness | 純粋性   | `CartForUpdate.add` が内側からリポジトリを呼ぶ |
| performance-purity       | 完全性   | 上限の判断がユースケースにある           |
| purity-completeness      | 性能    | 追加のたびに全アイテムをロードする         |

<span class="src">[examples/README](https://github.com/kawasima/boundaries-not-layers#examples)</span>

どれを選んでも具合が悪い。純粋性を「ドメイン層がI/Oを実行してよいか」というレイヤーの性質として捉えている限り、この三択から出られない。

純粋性は、単一の責務を持つ振る舞いの性質として捉え直す。

<!-- _class: veil -->

## 決めるのは、クラスの分類ではない

- どの値が有効か
- どの結果がありうるか
- 外部世界とどこで接するか

この3つを型で閉じる。ドメインモデルを業務を説明するクラス群として扱うのではなく、業務規則によって可能な状態と遷移を定める、実行できるモデルとして扱う。

---

<!-- _class: veil -->

## 境界を越えるとは、型を変えること

不正な状態のものを、内側に入れない。そのために境界では、入力を検査して通すのではなく、正しい型へ変換する。変換に成功した値だけが内側に入る。

- validate: 値はそのまま。正しさはフラグとして得るだけで、型には残らない
- parse: 正しければドメインの型になる。以降は型が正しさの証明になる
- 不正な状態のものは、そもそも内側の型を名乗れない

![境界](images/entrance.png)

## 境界の decode を担うライブラリ Raoh

**Raoh** は、境界の未確定な入力を、型のついたドメイン値へ変換（decode）する Java ライブラリ。

- 失敗は例外で飛ばさず、`Result`（`Ok` / `Err`）の値で返す
- どのフィールドで失敗したかを、パス付きで蓄積する（途中で止めない）
- record・sealed・パターンマッチが前提（Java 25）
- 入力源ごとにモジュールを足す。`raoh`（コア）に `raoh-json` / `raoh-jooq` を追加する

<span class="src">Maven Central: `net.unit8.raoh` ・ [github.com/kawasima/raoh](https://github.com/kawasima/raoh)</span>

---

<!-- _class: veil -->

## 検査（validate）ではなく変換（decode）する

`validate` は「この値は正しいか」を検査して bool を返す。値の型は変わらないまま内側へ流れていく。
`decode` は「正しければ、この型にする」。境界を越えた先では、型が正しさを保証している。

```java
public interface Decoder<I, T> {
    // 生の入力 → 型のついた値 or 構造化エラー
    Result<T> decode(I input, Path path);
}
```

<span class="src">[raoh（ライブラリ）decode/Decoder.java](https://github.com/kawasima/raoh/blob/main/raoh/src/main/java/net/unit8/raoh/decode/Decoder.java)</span>

parse, don't validate ── 検査して通すのではなく、境界で型に変える。

## 失敗を値で返す Result

```java
public sealed interface Result<T> permits Ok, Err {}

// 成功 ── 値を持つ
public record Ok<T>(T value)          implements Result<T> {}

// 失敗 ── エラーを持つ
public record Err<T>(Issues issues)   implements Result<T> {}
```

<span class="src">[raoh（ライブラリ）Result.java](https://github.com/kawasima/raoh/blob/main/raoh/src/main/java/net/unit8/raoh/Result.java)</span>

例外で大域脱出せず、成功と失敗を値で返す。`switch` のパターンマッチが `Ok` と `Err` の両方に向き合わせる。

`Ok` / `Err` は record（値がそろう「AND」）、`Result` は sealed（どちらか「OR」）。

## 状態の組み合わせを、record × sealed で型にする

注文者は個人か法人。**record**（値がそろう「AND」）と **sealed**（どれか一つ「OR」）を組み合わせると、この形をそのまま型にできる。

```java
public sealed interface Orderer permits Orderer.Individual, Orderer.Corporation {
    // 個人 = メール AND 氏名
    record Individual(Email email, String name) implements Orderer {}

    // 法人 = メール AND 会社名 AND 法人番号
    record Corporation(Email email, String companyName,
                       String corporateNumber) implements Orderer {}
}
```

<span class="src">[raoh/domain/Orderer.java](https://github.com/kawasima/boundaries-not-layers/blob/main/examples/raoh/src/main/java/com/example/cart/domain/Orderer.java#L11-L19)</span>

「法人なのに法人番号が無い」「個人なのに会社名がある」という組み合わせは、型として存在できない。

> Brian Goetz は "Data-Oriented Programming in Java" で、record と sealed を使えば「誤った状態を表現できない（make illegal states unrepresentable）」ようにモデリングできる、と述べている。

## 生の入力を、その場で型に変える

```java
public static final Decoder<JsonNode, Orderer> ORDERER = discriminate("type",
        variant("individual", INDIVIDUAL),
        variant("corporation", CORPORATION));

static final Decoder<JsonNode, Orderer.Corporation> CORPORATION = combine(
        field("email", string().trim().toLowerCase().email().map(Email::new)),
        field("companyName", string().trim().nonBlank().maxLength(200)),
        field("corporateNumber", string().pattern(Pattern.compile("\\d{13}")))
).map(Orderer.Corporation::new);
```

<span class="src">[raoh/web/JsonOrdererDecoders.java](https://github.com/kawasima/boundaries-not-layers/blob/main/examples/raoh/src/main/java/com/example/cart/web/JsonOrdererDecoders.java#L27-L41)</span>

## switch で網羅して分解する

```java
@PostMapping("/items")
public ResponseEntity<?> addItem(@RequestBody JsonNode body, Locale locale) {
    return switch (JsonCartDecoders.ADD_ITEM.decode(body)) {
        // 型引数はセレクタから推論される。ネストした record も var で分解できる
        case Ok(Tuple3(var userId, var productId, var quantity)) ->
                respondTo(tx.execute(status -> addItemToCart.apply(userId, productId, quantity)), locale);
        case Err(var issues) -> ResponseEntity.badRequest().body(errorBody(issues, locale));
    };
}
```

## 業務の判断は、手元の値だけで完結させる

```java
public record Cart(CartId id, TotalQuantity currentQuantity) {
    public static final int UPPER_BOUND = 10000;

            return Result.fail(Path.ROOT, "cart_full", "商品数の上限に達しています");
```

## I/O は、振る舞いの外で合成する

```java
public Result<CartItem> apply(UserId userId, ProductId productId, Quantity quantity) {
    return products.load(productId)                          // gateway: 商品を読む
            .flatMap(Product::ensureOnSale)                  // 振る舞い: 販売中か
            .flatMap(product -> carts.loadForUpdate(userId)  // gateway: カートを読む
                    .flatMap(cart -> cart.add(productId, quantity)  // 振る舞い: 上限内で追加
                            .map(item -> {                   // gateway: Ok のときだけ書き込む
                                carts.addItem(cart.id(), item);
                                return item;
                            })));
}
```

## Souther

ドメインを `data` / `invariant` / `behavior` で書く小さなJVM言語。書いたモデルから Java の record・sealed・decoder・encoder が生成される。

- 値の成立条件は `invariant` として型に書く。すべての構築経路で検査される
- 業務上の結果は、ただのデータの sum として並べる。失敗は言語の特別扱いではない
- 外部世界（DB・HTTP・時計・ID採番）の実装は言語の中に書けない。型だけを宣言する
- Java は生成物を使える。Souther から任意の Java API は呼べない

<span class="src">[github.com/souther-lang/souther](https://github.com/souther-lang/souther)</span>

---

<!-- _class: veil -->

## 有効な値を、型の成立条件として書く

```souther
data Quantity = Int
    invariant value > 0
data TotalQuantity = Int
    invariant value >= 0
data Email = String
    invariant String.length(value) >= 3      // a@b が最短。形式は境界の raoh が見る

// カートに入れようとしている明細。上限を超えないことは、この型の成立条件
data PendingItem = { cart: Cart, item: CartItem }
    invariant withinCapacity = cart.currentQuantity.value + item.quantity.value <= 10000
```

<span class="src">[raoh-souther/src/main/souther/cart.sou](https://github.com/kawasima/boundaries-not-layers/blob/main/examples/raoh-souther/src/main/souther/cart.sou)</span>

不変条件は、すべての構築経路で検査される。境界の decoder では Raoh の `Result` の失敗になり、モデルの内側では abort する。内側で違反するのは業務上の結果ではなくモデルの誤りだからである。

`requirePositive` を書く場所は、もうどこにもない。

## ありうる結果を、並べて書く

```souther
behavior addItemToCart : (userId: UserId, productId: ProductId, quantity: Quantity)
        -> ItemAdded | ProductNotFound | SaleEnded | CartFull
    depends on loadProduct, loadCart, saveItem

let addItemToCart (userId, productId, quantity, loadProduct, loadCart, saveItem) =
    match loadProduct(productId) with
        | ProductNotFound -> ProductNotFound
        | Product { id, onSale, price } -> {
            guard onSale else SaleEnded
            let c = loadCart(userId)
            guard PendingItem { cart = c, item = CartItem { productId = productId, quantity = quantity } } as pending
                else | withinCapacity -> CartFull
            saveItem(pending)
        }
```

<span class="src">[raoh-souther/src/main/souther/cart.sou](https://github.com/kawasima/boundaries-not-layers/blob/main/examples/raoh-souther/src/main/souther/cart.sou)</span>

成功も却下も同じ並びのデータ。例外も、成功／失敗の二分もない。

上限の判断は `guard` の条件ではなく、`PendingItem` の成立条件（`invariant withinCapacity`）に置いた。構築を試みて、成立しなければその節の名前で `CartFull` へ departure する。ルールは型に1回だけ書かれ、呼ぶ側がそれを書き写すことはない。

## 例が足りているかを、モデルに問う

```text
$ souther examples src/main/souther/cart.sou
  addItemToCart            implemented   rows 6    pending 0
    signature   out specified 4/4  observed 4/4  verified 4/4
    border      borders 3   coverage items 6/6   excluded 6
    branch      6/6

```

数えているのは、テストのカバレッジではなくモデルが述べたことである。出力の sum のケース、入力の sum のケース、`invariant` や `guard` が引いた境界、本体の分岐。どれも書いた本人がモデルに書いたもので、その一つひとつに行があるかを問う。

モデルが線を引いていない位置は、埋めるべき穴として数えない。`--strict` を付ければ、埋まっていない指摘でビルドが落ちる。

## Raoh と Souther の継ぎ目

```java
        field("email", string().trim().toLowerCase().email()),               // 正規化と形式検査は raoh
```

## まとめ

- 有効な値は境界で型にする。内側では同じ検査を繰り返さない
- ありうる結果は型に並べる。業務上の却下を例外や真偽値にしない
- 時計もDBも外部世界として境界に置き、判断は手元の値だけで完結させる
